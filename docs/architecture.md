# System architecture and MVP roadmap

## Boundaries

- `src/app`: App Router pages, layouts, route handlers, and thin Server Action entry points.
- `src/features`: vertical features (`teams`, `league-settings`, `roster`, `recommendations`, `reports`) containing schemas, services, actions, and components.
- `src/features/recommendations`: pure deterministic domain code with no framework or database dependency.
- `src/lib`: Prisma, authentication, OpenAI, observability, and shared infrastructure adapters.
- `prisma`: canonical relational schema and migrations.

Request flow: UI → validated Server Action/route → authorization → application service → Prisma repository → deterministic engine → persisted result → optional OpenAI explanation → UI. All external projection providers implement a common normalized-player/projection adapter so Sleeper, ESPN, Yahoo, and FantasyPros do not leak vendor shapes into domain code.

## Data model

`User` owns many `Team` records. Each team has one `LeagueSettings`, many `RosterPlayer` records, and historical recommendation snapshots. A player's provider-specific weekly facts are normalized into `WeeklyProjection`. Recommendation outputs are persisted as JSON snapshots plus algorithm versions so old advice remains reproducible when algorithms change. Key ownership, weekly lookup, external ID, and priority queries are indexed in the Prisma schema.

Roster slots are JSON because custom leagues need arbitrary counts. Validate them at the boundary with a versioned Zod schema; migrate old shapes explicitly. In a later integration phase, introduce canonical `Player` and provider-ID tables so one NFL player can be shared across teams without duplicating provider identity.

## Scoring and projections

Raw stat projections must be converted to fantasy points using the league's passing, rushing, and receiving weights before optimization. Store raw provider payloads for traceability but only expose normalized projections to the engine. Blend multiple sources with explicit configurable weights and record the blend version.

## Lineup optimization

The optimizer performs an exhaustive constrained assignment for MVP-sized rosters. A player can fill one slot; slot eligibility is explicit; the objective maximizes the sum of health-adjusted projections plus small, bounded matchup and consistency modifiers. Exhaustive search avoids the classic greedy FLEX/SUPERFLEX mistake and is practical for normal roster sizes. For large custom formats, replace the search implementation with maximum-weight bipartite matching while retaining the interface.

Confidence is derived from the margin between each starter and its best eligible bench alternative, then clamped to a user-friendly range. Alternatives are the smallest-margin valid swaps. Missing required eligibility produces a domain error rather than an incomplete lineup.

## Waiver ranking

Each available player is compared with the weakest relevant roster replacement. Priority combines near-term adjusted projection, six-week/rest-of-season value, upside, projected gain over the drop, and position scarcity. The constants are versioned product policy—not generated by AI—and should later be calibrated against historical outcomes. K/DST scarcity is deliberately discounted. Results are deterministic, sorted, and capped at ten.

Drop protection should be added in Phase 3 for elite starters, injured-reserve slots, recently acquired players, and user-locked players. Waiver availability is league-specific and must never be inferred globally.

## AI boundary and safety

OpenAI receives only structured, already-ranked facts: player names, deltas, matchup/injury facts, confidence, and league format. Use JSON-schema structured output, low temperature, prompt versioning, timeouts, and a non-AI template fallback. Never send secrets or let generated text change scores. Cache explanations by recommendation ID and prompt version.

## Incremental implementation roadmap

## MVP data architecture update

`User` owns leagues and managed teams. `League` owns shared `LeagueSettings` and can contain multiple `Team` records. `RosterPlayer` represents team membership and points at a canonical `Player`; provider identifiers live in `PlayerExternalId`. Imported projections, rankings, injuries, and NFL matchup facts attach to canonical players through `DataProvider`, while recommendations and waiver availability remain team-specific.

Projection consumers depend on the normalized contract in `src/features/projections/provider.ts`. The repository gives manual team input precedence and then consumes imported sources without exposing provider payloads to the optimizer. See `docs/provider-contracts.md` for adapter requirements.

1. **Foundation (complete):** responsive dashboard shell, complete initial Prisma schema, deterministic optimizer/waiver engine, unit-test seam, architecture decisions, environment contract.
2. **Team setup (complete):** database-backed authentication, Prisma client and initial migration, team CRUD, roster editor, custom Zod-validated settings, ownership checks, and accessible forms.
3. **Live recommendations (complete):** manual point/stat projections, scoring conversion, Server Actions, lineup persistence, waiver entry/ranking, and algorithm-versioned snapshots.
4. **AI reports (complete):** structured OpenAI explanations, deterministic fallbacks, weekly report composition, and fact-constrained prompts.
5. **Production baseline (complete):** security headers, health endpoint, responsive error states, migrations, Docker PostgreSQL option, deterministic tests, and Vercel build support. Provider sync jobs, richer observability, end-to-end browser tests, and managed backup policy remain deployment-specific operations.
6. **Expansion:** canonical player identity, Sleeper first adapter, then ESPN/Yahoo/FantasyPros; dynasty/keeper value horizons, trade analyzer, and league power rankings as separate deterministic engines.

## Phase acceptance criteria

Phase 2 is complete when a signed-in user can create multiple isolated teams, save custom scoring/slots, add/edit/delete roster players, and reload everything from PostgreSQL. Phase 3 is complete when the same input always yields the same legal lineup and waiver ordering, every recommendation stores its algorithm version, and integration plus edge-case tests pass.
